*Research Report / 2026-09-13*

# 脱WordPressは SEOに悪影響なのか

AIにソースを書かせた実在サイトの調査と、WordPressを外すことのSEO影響の検証。月間1.6〜2万セッションの既存SEO資産を持つ manebi.co.jp のフルリニューアルという文脈で、実務的な結論を出す。

*依頼：**マーケティング部 松尾** 調査：**26ソース／242論点を抽出・検証** 関連：**リニューアル要件定義書 v1.6***

## 結論 先に3行

### ① CMSの種類はGoogleのランキング要因ではない。WordPressを外すこと自体にSEOの不利益はない。

Googleが複数回、公式に明言している。ここは争点ではない。逆に「WordPressだから有利」ということもない。

### ② 順位が落ちる原因は「CMSを変えたこと」ではなく「移行で壊すこと」。そしてそれは高頻度で起きている。

同じWordPressのままドメインだけ変えて流入を9割失い、回復に1年半かかった実例がある。CMS非依存のリスクであり、今回のリニューアルでも同じ危険がある。

### ③ manebiの結論：WordPressは残す。ただしテーマ実装にAIコーディングを使う。

SEOが理由ではない。①AI集客エンジンがWordPress下書き前提で組まれている ②非エンジニアの日常更新はヘッドレスの弱点だとベンダー自身が明言 ③AI検索クローラはJSを実行せずLLMO投資と衝突する——の3点。詳細は最終セクション。

## Q1 AIにソースを書かせた実在サイト

「AIが全部書いた本番サイト」は2026年に入って実名事例が出てきた。ただし**見つかった事例はすべて小規模で、月間数万セッション級のSEO資産を持つサイトの事例は存在しない**。これが今回の調査で最も重要な発見のひとつ。

### F2T（f2t.jp）— コーポレートサイト `[Claude Code]`

*Next.js 16 + Tailwind CSS 4 + microCMS + Vercel ／ 2026年4月公開 ／ 企画からデプロイまで約1日*

AIエージェント開発企業が自社サイトをClaude Codeとの対話のみで構築。OGP・XMLサイトマップ・構造化データ（Person × Organization × BlogPosting）までAIが実装。実装コストは制作会社見積もりの1/3〜1/5と自社報告。

**移行元はWordPressではなくWebflow。**離脱理由は「独自構文のためAIエージェントがコードレベルで操作できない」——SEOではなく**AIが扱えるかどうか**というCMS選定基準。

実害：トップページのブログセクションが旧サイトのURLを指したままで404が発生し、手作業でのURL移行が必要になった。

### talental（talental.jp）— コーポレートサイト `[Claude Code]` `[脱WordPress]`

*Claude Code + Astro + Vercel + Notion(DB) + Cloudflare + Resend ／ 2026年3月 ／ 着手から公開まで2日＋調整1日*

WordPress＋プラグイン構成を意図的に捨てて全面再構築した、数少ない「本当の脱WordPress × AI生成」事例。「表示の軽さは明らかに出やすくなった」と定性報告（CWV実測値の提示はなし）。

**事故が3件記録されている：**DNS設定ミスで関連2サイトが一時404／旧記事の画像パスが崩れて画像が全非表示／ページごとにトンマナが少しずつズレる。

そして最も重要な点：**日常更新用のCMS管理画面は作っていない。「いったん自分だけが触る前提」**。非エンジニアの運用は解決していない。

### ジカーズ（中古車査定）— サービスサイト＋オウンドメディア `[Claude Code]`

*Claude Code + Astro + Tailwind + MDX + Vercel ／ 2026年4月 ／ 構築者は非エンジニア（UXデザイナー/PdM）*

CMSを「人間が触るもの」から「AIが触るもの」に作り替えた事例。編集UIは管理画面ではなく**Claude Codeのスラッシュコマンド**（`/article`、`/article-news <URL>`、`/article-bulk`、`/article-cluster`）。SEOのピラー＋クラスタ記事生成までワークフロー化されている。

移行元はSTUDIO（ノーコード）。離脱理由は順位ではなく、月50本以上の記事に対しサムネ差し替え・本文流し込み・関連リンク調整・構造化データ確認という手作業が積み上がる運用負荷。

品質担保として検証フック3種（存在しないニュースソース検出・用語lint・frontmatter必須項目チェック）とZodスキーマを実装。**「ユーザー承認なしでのpushは禁止」**を明文化。

### covid19.teraren.com — 4,700記事のオウンドメディア `[Claude Code]` `[脱WordPress]`

*WordPress → Astro + Cloudflare Pages ／ 2025年10月 ／ 記事数4,700*

唯一の「記事数が多い」脱WordPress×AI事例。WordPressのXMLからMarkdownへの変換処理をClaude Codeが実装。**4,700ページのビルドが10秒**、デプロイ全体でも約7分。運用コストは月額ゼロ（Cloudflare無料枠）。

SEO面の実装：**301リダイレクトを使わず、既存URL構造をそのまま再現する方針**（記事数が多くリダイレクト管理が現実的でないため）。サイトマップは `@astrojs/sitemap` が自動生成、サイト内検索は Pagefind で代替。

ただし**「PVはほとんど無い」個人サイト**であり、SEO資産の保全という観点での検証にはならない。ビルド時間短縮のため画像最適化を省いた結果、記事ページのLighthouseスコアは低い。

| サイト | 構成 | 結果 |
| --- | --- | --- |
| Webクリエイターボックス<br>2010年開設・記事1,000件超 | WordPress（15年）→ Next.js + Vercel + microCMS（2025年） | 動機はSEOではなく**動作の重さとセキュリティ懸念**。Lighthouseスコアが大きく改善。ただしSEO影響・URL変更・リダイレクト設計への言及が一切なく、検証材料にはならない |

## Q2 CMSはランキング要因か — 明確にNO

ここは議論の余地がない。Googleが複数回、公式に否定している。

> 我々の検索システムは、特定のCMSを識別して異なる扱いをすることはない。Googleにとって、CMSはWebページを作る手段のひとつにすぎない。
>
> — *John Mueller（Google Search Advocate）／ Ask Googlebot, 2022年7月*

> Googleのシステムはページがどう作られたかに注目しない。最終結果に注目する。手で書いたWebページは、WordPressやWix、Squarespaceが生成したものと同じくらい良いものになりうる。
>
> — *同上*

> 主要なCMS間にSEOの本質的な違いはない。モダンなフレームワークによる静的ホスティングでも問題ない。／ WordPressを使うことによる順位のブーストは存在しない。
>
> — *John Mueller ／ Reddit, 2025年10月*

Muellerが挙げた判断基準はシンプルで、**「クロール可能なHTMLを出力し、まともなナビゲーションがあるか」**だけ。これがAI生成・静的サイトの合否判定の実務的な基準になる。

補強データとして、Mueller自身が Web Almanac 2024 を引用している：**全サイトの51%がCMSを使っているが、上位1,000サイトでは8%しか使っていない**。大規模・高可視性のサイトほど、むしろ従来型CMSなしで運用されている。

### AI生成コードであること自体もペナルティにならない

> 実際のところ、誰も「これはvibe codingされたサイトだ」と見分けることはできない。
>
> — *John Mueller ／ 2026年5月（Search Engine Journal報道）*

### ただしMuellerは同じ場で、AI構築サイトの決定的な弱点を指摘している

> canonicalやサイトマップ、robots.txtといったSEOの基本は、AIツールがサイトを作ったというだけで勝手に設定されるわけではない。
>
> — *同上*

実際にAI構築サイトでは、canonicalタグの欠落、XMLサイトマップの不在、**JavaScriptファイルを誤ってブロックするrobots.txt**、弱いHTML構造と内部リンクが頻発する。「SEOも入れといて」という曖昧な指示では不正確な結果しか出ない。技術指示を出せる人間が各工程に必要で、AIに丸投げできる領域ではない、というのがGoogle側の見解。

## Q3 では何が順位を落とすのか

CMSではなく**移行という行為そのもの**。しかもこれはWordPressを使い続けても発生する。

### Google公式：一度に1つだけ変えろ

> 一度に1つのことだけ変更しなさい。サイトへの変更は、全部同時にではなく、順番に計画しなさい。
>
> — *Google Search Central「Site moves with URL changes」<sub>検証 3-0</sub>*

同ドキュメントは「CMSを変更する」「新しいレイアウトに更新する」を**同時にやらず1つずつ実施すること**を名指しで推奨している。今回のリニューアルはIA変更・デザイン刷新・テンプレート刷新をすでに含むので、ここにCMS基盤の変更まで重ねるのはGoogle公式ガイダンスに正面から反する。

また「大きな変更をすれば、再クロール・再インデックスの間、順位は変動する」とも明記されており、**移行直後の順位下落それ自体は失敗の証拠ではない**。中規模サイトで新URLが置き換わるまで数週間以上、大規模ではさらに長い。判断には最低でも数週間〜数ヶ月の観測期間が要る。

### 実例：同じWordPressのまま、流入9割減・回復1年半

hooshmand.net の事例は示唆的で、**CMSは変えずドメインだけ移転**した結果、1日1,000超あった検索流入が200→100→50と落ちた。301リダイレクトはCloudflareのエッジで実装され技術的には正しく返っていたが、評価が移らなかった。原因として特定されたのは**旧XMLサイトマップが404を返していたこと**と、リンク先アセットのリダイレクト漏れ。移行後9ヶ月間、Core Web Vitalsレポートにトップページしか現れなかった＝新URLがほぼ再クロールされていなかった。

同記事が引く `ancient.eu → worldhistory.org`（月間300万セッション超）は、約6週間ほぼ全流入を失い、元の水準に戻るまで約1年かかっている。

### 移行事故の原因トップ

| 原因 | 内容 |
| --- | --- |
| **noindexの消し忘れ** | 壊滅的な流入喪失の筆頭原因。ステージング環境のサイト全体noindexが公開時に外されず、全ページがGoogleに「インデックスしないで」と伝え続ける |
| リダイレクトチェーン | 中間URLがrobots.txtでブロックされている構成 |
| canonicalの誤設定 | インデックスすべきページをスキップさせる／存在しないURLを指す |
| **静的HTMLだったものがJS配下に移動** | JS重量級アーキテクチャへの移行時に必須の診断項目として名指し。これがまさにNext.js/Astro/AI生成コードのリスク |
| 内部ナビの削除 | リンク評価を運んでいたナビゲーションメニューを消すこと自体が独立した順位リスク |

出典：Sitebulb「When Website Migrations Go Wrong」。同ガイドは**移行前にロールバックの判定基準を定義しておくこと**を推奨し、新サイトに問題が深く埋まっている場合は旧サイトへの差し戻しを正当な判断として扱っている。Google公式ドキュメント上、アドレス変更の申請後に旧ドメインの扱いが完全に解消されるまで約180日。

補足：Google公式のJS SEOガイドは、SPAのルーティングにHistory APIを使うこと、フラグメント（#）で本文を切り替えないことを明記している。<sub>検証 3-0</sub>

## Q4 JavaScriptとレンダリング — ここがLLMOと衝突する

### Googleに対しては問題ない（実測）

Vercel × MERJ の実測調査（2024年4月、nextjs.org他で10万回超のGooglebotフェッチ、37,000件のビーコン照合）：

- **200を返すHTMLページの100%が完全にレンダリングされた**。クライアントサイドのAPI呼び出しやReact Server Componentsのストリーミングを含む
- 「レンダリングキューは長い」という通説は誤り。クロールからレンダリング完了まで**中央値10秒**（25パーセンタイル4秒）。ただしロングテールがあり、90パーセンタイル約3時間、99パーセンタイル約18時間
- **クエリ文字列つきURLは著しく遅い**（75パーセンタイルで31分 vs クリーンURLの22秒）
- 初期HTMLに `noindex` があるとレンダリング自体が止まる。**JSで後から消しても無効**
- URLエンコードされたリンク（`https%3A%2F%2F`）は発見されない＝リンク評価を失う

クロール効率の評価は**CSRが「Poor」、静的生成（SSG）が「Excellent」**。Google公式も、純粋なクライアントサイドレンダリングよりサーバーサイドレンダリング／プリレンダリングを推奨している。<sub>検証 3-0</sub>

### しかしAI検索クローラはJavaScriptを実行しない

ChatGPT（OpenAI）・Perplexity・Claude のクローラは**クライアントサイドJSをレンダリングしない**。CSR依存のサイトは、これらのプラットフォームからは「空白ページ」に見える。実地テストでChatGPTは「JavaScriptベースのレンダリングに依存しているためページ内容を読めない」と明示的に回答し、Perplexity・Claudeでも同じ失敗が再現している。

影響は「引用されない」だけでなく、ChatGPTの「More」欄やPerplexityの「Reviewed」欄への格下げ（Citationsに載らない）、スニペット欠落として観測されている。

**manebiはLLMO対策にS&Sへ400万円を投資している。**CSR寄りの実装はその投資と正面から衝突する。JS構成を採るなら全ページSSG/SSRが必須条件になる。

## Q5 非エンジニアの日常更新は成立するか

ここが今回の調査で最も判断を左右した論点。**ヘッドレス化を売っているベンダー自身が「非エンジニアの更新」を非推奨対象に挙げている。**

> ヘッドレスCMSを導入すべきは、①最新のJSフレームワークが利用できるフロントエンドエンジニアやWebデザイナーがいる会社 ②サイトの規模がそこまで大きくなく、高頻度にデザインの変更が必要なサイトを持っている会社。
>
> — *LYZON（ヘッドレス／従来型CMS両方を提供するベンダー）*

同社は**「大量のコンテンツを効率よく管理したいユーザー」「JSのスキルのないユーザーが簡単にサイトを更新できるCMSを作りたいユーザー」を明確に非推奨対象**としている。実際の失敗例として、社内にWebデザイナーがいてもTypeScript/Reactの改修とデータ構造の理解が想定以上に難しく、運用費が激増したケースを挙げている。

ブースターテクノロジー（移行支援を売る側）も同様に、非エンジニアが管理画面から更新したいならAstro単体では不十分でヘッドレスCMS併用を推奨、適用条件は「更新頻度がそれほど高くない、または開発チームが更新フローに関与できる」こと、としている。

### 成立している事例の共通点＝ヘッドレスCMS併用

| 事例 | 非エンジニア運用 |
| --- | --- |
| F2T | `[成立]`microCMSの日本語管理画面。ただし無料枠は月間APIリクエスト10,000回 |
| Webクリエイターボックス | `[成立]`microCMSは「APIキー等の触ってはいけない領域」と「操作して良い領域」が明確に分離 |
| ジカーズ | `[成立]`ただしGUIではなくスラッシュコマンド。運用者はUXデザイナー/PdMでCLIに抵抗がない層 |
| talental | `[未解決]`管理画面を作っておらず「自分だけが触る前提」 |

### 失われる機能と代替手段（技術的にはすべて代替可能）

| WordPressで得ていたもの | ヘッドレス構成での代替 | コスト |
| --- | --- | --- |
| Yoast/RankMathのメタ管理 | CMS側にSEOフィールドのスキーマを自作（例：Sanityの `seoFields` 型でtitle/description/canonical/robots/OGP/hreflang/カスタムmetaを一括提供）。編集画面内のライブSEOプレビューも実装可 | プラグイン導入ではなく**開発** |
| XMLサイトマップ自動生成 | `@astrojs/sitemap` 等で自動生成可。ただし `lastmod` の正確性が要件（Googleが再クロール優先度に使う）、5万URL超はインデックス分割 | 低 |
| 構造化データ | ヘッドレスでは自動出力されず**フロントエンド側で手実装**が必要。スキーマ型＋レンダーヘルパーは提供されている | 中 |
| リダイレクト管理 | CMSにredirectドキュメント型（source/destination/permanent/enabled）を持たせ編集者が管理する設計が公式に提示されている。**ただしVercelのNext.js configリダイレクトは1,024件上限**、超える場合はミドルウェア自作 | 中〜高 |
| canonical管理 | ヘッドレスは「バックエンドURL＋フロントURL」の重複インデックスリスクがあり、意図的な設定が必須 | 中 |

参考値：Core Web Vitalsの3指標すべてを満たすページは、1つでも落ちるページより約10%多くオーガニッククリックを得る（Google Search Central 2025、Jottler経由）。静的化の効果はゼロではないが、順位への直接効果は各ソースとも「間接的・限定的」と慎重に書いている。

## Q6 AI生成コード特有のリスク

SEOとは別枠で、定量データが揃っている領域。いずれも一次調査。

| 領域 | 実測データ | 出典 |
| --- | --- | --- |
| **セキュリティ** | LLMが生成したコードの**45%のテストケースでセキュリティ脆弱性が持ち込まれた**。100超のLLMをJava/JavaScript/Python/C#で横断評価。**モデルが新しく大きくなっても改善しない**（＝最新モデルを使えば安全、は成り立たない） | Veracode 2025 GenAI Code Security Report |
| **保守性** | 2023〜2026の6.23億件のコード変更を分析。コードブロックの重複が**81%増**（40.3→73.0／百万行）、リファクタリングは**21%（2022）→3.8%に崩落**、ファイル跨ぎの関数呼び出し35%減、レガシー保守74%減。開発者はリファクタするより**約5倍コピペしやすい** | GitClear「The Maintainability Gap」2026年1月 |
| **アクセシビリティ** | 査読論文。ChatGPT 4o / Copilot Pro / Claude 3.7 Sonnet / Grok 3 は意味的に妥当なHTMLは書けるが、**追加プロンプトと人間の介入なしにWCAG 2.1完全準拠には達しない**。フォームやテーブル等のB2Bサイト頻出UIで検証済み | Universal Access in the Information Society, 2025年7月 |
| **情報漏えい** | vibe codingツール（Lovable/Base44/Replit/Netlify）製の公開資産38万件をスキャンし、**約5,000件が機微な企業・個人情報を露出**。医療記録・金融データ・Fortune 500の社内文書を含む。**主因はコード品質ではなく「初期設定が公開」＋非エンジニア運用者** | RedAccess調査 ／ Axios 2026年5月 |
| 一貫性 | ページ単位でAIに作らせると個別ページは成立するが、**サイト全体でトンマナが徐々にズレる**（当事者の実務報告） | talental |

GitClearの結論は「AIが悪いコードを書く」ではなく、**デフォルトのAIワークフローが「通ったテスト・閉じたチケット」という原子的成果に最適化されている**ことが原因、という整理。つまり規律あるレビュー工程で緩和できる性質の問題。Axiosの漏えいも同様にガバナンスの問題で、組織的統制があれば回避できる。

ただしいずれも「人間のレビュー工程を組み込むこと」が前提条件になる。**公開まで2日**のような速度は、この前提と両立しない。

## 結論 manebi.co.jp への実務判断

### WordPressを外すこと自体はSEOリスクではない。だが今回のリニューアルで外すべきではない。

理由はSEOではなく、以下の3点。

1. **AI集客エンジンがWordPress前提で組まれている。**島崎さんのエンジンは講座LP・記事・FAQ・構造化データを `forceDraft()` でWordPress下書きとして生成し、公開ボタンは人間がWP管理画面で押す設計になっている。CMSを外すと、この入稿経路と承認フローを丸ごと作り直すことになる。要件定義v1.6の運用要件（教材数8,000等のグローバル値管理、CTAのブロックパターン化、比較表のデータ管理）も同じくWP管理画面前提。
2. **非エンジニアの日常更新はヘッドレスの構造的弱点。**ヘッドレスを売るベンダー自身が「大量コンテンツを効率よく管理したい」「JSスキルのないユーザーが更新する」用途を非推奨に挙げている。manebiは月6本のリライト運用を非エンジニアが回しており、まさにこの非推奨条件に該当する。
3. **AI検索クローラはJSを実行しない。**LLMOに400万円を投じている以上、CSR寄りの構成は投資を毀損する。仮にJS構成を採るなら全ページSSG/SSRが絶対条件になり、その制約下でWordPressより優れる根拠は今回の調査では見つからなかった。

### 一方で、AIコーディングは全面的に使うべき

今回の事例が示したのは「WordPressを捨てるべき」ではなく、**AIエージェントが扱いやすいコードベースかどうかが新しい選定基準になった**ということ（F2TがWebflowを捨てた理由がまさにこれ）。WordPressはPHPテーマという素のコードで動くので、**Claude Codeでテーマを実装するのは何の障害もない**。ここが最も費用対効果が高い。

- テンプレート13種の実装をAIコーディングで行い、制作コストを圧縮する
- ページビルダー系プラグイン（独自構文でAIが触れない）は採用しない。**素のPHPテンプレート＋ブロックパターン**で組む
- 速度改善はWordPressのままでも可能（静的キャッシュ、画像最適化、不要プラグイン削減）。CWVは「3指標達成で約10%クリック増」程度の間接効果であり、基盤を捨てる理由には足りない

### リニューアルに必ず組み込む安全装置

CMSを維持しても、今回はIA変更・URL新設・テンプレート刷新を伴うため、Q3の事故はそのまま起こりうる。以下を要件定義書に反映する。

| 装置 | 内容 |
| --- | --- |
| 段階リリース | Google公式「一度に1つだけ変えろ」に従い、**T9コラムCTA先行 → 新設ページ群 → 既存ページ刷新**の順で分割公開。順位変動の原因を切り分けられる状態を保つ |
| URL温存を第一原則 | 既存URLは原則変更しない（要件定義v1.6の方針を維持）。covid19事例と同じく**リダイレクトより「URLを変えない」ほうが安全** |
| 公開前チェックリスト | ①staging noindexの解除確認 ②リダイレクトチェーンとrobots.txtブロックの検査 ③canonicalが実在URLを指すか ④旧サイトマップが404を返していないか ⑤JSファイルをrobots.txtでブロックしていないか ⑥内部ナビから消えるリンクの棚卸し |
| ロールバック基準 | 公開前に「どの指標がどれだけ落ちたら戻すか」を数値で決めておく。判断には数週間〜数ヶ月の観測期間が要ることも事前に合意しておく |
| AI生成コードのレビュー工程 | セキュリティ（45%に脆弱性）・アクセシビリティ（WCAG非準拠）・重複コードは人間のレビューでしか止まらない。速度優先で工程を飛ばさない |
